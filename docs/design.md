# How the formatter works, and why

This is the design writeup behind the formatter's source — the *what* lives in each file's own header comment (kept in sync with this doc); this covers the *why*, the internals worth knowing before touching the table engine, and pitfalls that already bit us once.

## File layout

The formatter is split by concern, not left as one large file — the file you want is usually the answer to "where does X happen":

| File                 | Answers                                                                                                                                                                                              |
| -------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `markdown-format.ts` | The orchestrator — `formatMarkdown`/`minifyMarkdown`, wiring the passes below into the one function Codon and the CLI call. Read this file first; it's the pipeline's shape, not its internals. |
| `frontmatter.ts`     | Where do we detect YAML frontmatter?                                                                                                                                                                 |
| `mdc.ts`             | Where do we detect MDC block components (`::name … ::`)?                                                                                                                                             |
| `fences.ts`          | Where do we detect fenced code blocks and multi-line HTML comments — the shared fence-toggle mdc.ts, tables.ts, and list-tighten.ts all key off, instead of each keeping its own copy?               |
| `reflow.ts`          | Where do we join wrapped paragraphs/list items onto one line?                                                                                                                                        |
| `list-tighten.ts`    | Where do we drop blank lines between simple list items?                                                                                                                                              |
| `tables.ts`          | Where do we format PLAIN GFM pipe tables (width 0, always) — parsing, column widths, cross-table matching, emission?                                                                                 |
| `grid-tables.ts`     | Where do we format GRID tables (width N > 0, always) — border-delimited cells, real colspan?                                                                                                         |
| `eol.ts`             | Where do we detect/normalize line endings?                                                                                                                                                           |
| `discover.ts`        | Where do we find project-wide markdown files (`discoverMarkdownFiles`, the CLI's `--git-driven`/`--all`)?                                                                                            |

`frontmatter.ts`, `mdc.ts`, and `fences.ts` exist for **detection only** — `reflow.ts`, `list-tighten.ts`, and `tables.ts` each call into them to find out which lines to leave completely alone, rather than duplicating that detection logic. `fences.ts` is the newest of the three (see the pitfall below for why it had to stop being duplicated).

## The contract, restated

- **Idempotent** at every width: `format(format(x)) === format(x)`.
- **Pipeline-stable**: `format(serialize(parse(format(x)))) === format(x)` — one save cycle of already-formatted text changes nothing. This half of the contract can only be verified against a real markdown-editing pipeline (parse → edit → serialize), which needs a DOM (jsdom) — this package deliberately doesn't have one, so that half is pinned in the **consumer** repo instead: [jurijsk/codon](https://github.com/jurijsk/codon)'s `test/formatParity.test.ts`, which imports this package and drives it against Codon's real TipTap/ProseMirror pipeline. If you change table/paragraph layout here, that test is the one that actually proves you haven't broken the editor round-trip — running only this package's own test suite isn't sufficient.
- **Layout-only**: never touches inline spelling (emphasis markers, escape sequences, link encoding, list renumbering). A formatter that also normalized `*x*` → `_x_` would be a different, riskier kind of tool — this one only ever moves whitespace and line breaks.

## The table engine

### Two width regimes, not a spectrum

`tableWidth` is not "pick any wrap column" — it's binary in shape, and as of this section's latest rewrite, the two regimes use two DIFFERENT on-disk syntaxes, not just different widths of the same one:

- **`0`** — every logical row becomes exactly one raw-file line of **plain GFM pipe syntax**, padded so pipes align down the page (`tables.ts`). This is the **logical / commit form**: the byte-for-byte layout every other GFM renderer (GitHub, GitLab, whatever) understands correctly, and the only width this ever uses pipe syntax's own "fewer cells than the header renders blank" convention for a whole-row-spanning note (see "Sparse rows" below) — there is no colspan in real GFM.
- **`N` where `N ≥ 40`** — cell text wraps onto a **grid table** (`grid-tables.ts`): a Pandoc/reStructuredText-style `+---+---+` / `|` bordered table, where cell boundaries come from the border lines' fixed character positions rather than being inferred from content shape. See "Grid tables" below for the full design — this replaced an earlier, narrower "continuation row" convention (a raw-file row whose first cell was empty, carrying the wrapped tail of the row above) that this section used to describe; that mechanism's known failure mode — a continuation row is indistinguishable from a genuinely short row whenever the FIRST column is what wraps — is exactly what grid tables were built to eliminate structurally instead of working around with a better heuristic.
- Values `1–39` clamp up to 40 (`MIN_TABLE_WIDTH`) — below that the shrink-to-fit loop can't do anything useful with real cell content.
- **This is why 0 is the only commit-safe width** (see the CLI section below): grid-table syntax outside this formatter's own reader is, at best, understood by Pandoc/reST-aware tooling and, at worst (plain CommonMark/GFM, e.g. viewing the raw file on GitHub mid-edit), rendered as a literal paragraph of border punctuation — readable, not broken, but not a table.

### Width-0 padding has no cap — alignment always wins

At width 0, columns pad to their widest cell, uncapped. An earlier version capped padding at 80 chars (`MAX_PAD_WIDTH`) so a monster cell (a key-value dump running to thousands of characters, which real fixtures in Codon's `examples/` corpus actually contain) wouldn't force every *other* row in that column to pad out to match it — past the cap, the monster cell kept its full content and simply overflowed its own column, alignment giving up before content did. That traded away the one thing width-0 exists to guarantee: every row's pipes actually line up. The cap is gone now — a genuinely huge cell inflates its column's padding for every row, which is the correct trade for a regime whose entire purpose is visual alignment. Content is still never truncated.

### The shrink-to-fit loop (width N)

`computeColumnWidths` starts every column at its natural (longest-cell) width, then — only when fitting to a target `maxLineLength` — repeatedly shrinks the currently-widest column by one character until the total line length fits or every column has hit its **floor**. A column's floor is the longer of: its header cell (a GFM header can't wrap; the delimiter row must sit on the very next line) and the longest whitespace-unbreakable token in any body cell. If the floors alone don't fit the target, the table settles at the minimal width *above* the target that keeps every word whole — wider than asked, never with a word sliced (a sliced `idempo`/`tent` would round-trip back together as `idempo tent`, corrupting content).

### Sparse rows — GFM's row-spanning-note convention (no real colspan), width 0 only

Since grid tables (below) took over `tableWidth > 0` entirely, everything in this section is specifically about `tableWidth: 0` — plain GFM pipe syntax, which still has no real colspan and still needs this convention. At `tableWidth > 0` a "sparse row" isn't a special case at all any more; it's just an ordinary cell with `colSpan === cols` (see `parsedTableToGridTable`) rendered as one wide box like any other span.

Pipe tables have no colspan: a cell cannot visually span multiple columns. What authors actually write for a note that should read as spanning the whole row is a **sparse row** — GFM's own rule for a row with fewer cells than the header is to render the missing trailing cells as empty, and every renderer already does this on its own, so a single `| Comment: … |` row under a 5-column header reads as a whole-row note by convention.

The formatter only treats a row this way when it has **exactly one cell**, not merely "fewer than the header." A row with 2..cols-1 cells (e.g. a 5-column row missing only its last, usually-blank column) is far more likely a typo — someone dropped a trailing `|` — than a deliberate spanning note, so `scanTables` pads it to `cols` and treats it as an ordinary (if ragged) row, same as a row with MORE cells than the header already was. Treating every "fewer than the header" row as a spanning note used to also catch these near-full rows: excluded from column-width computation and rendered unaligned with the rest of the table, at whatever width its own content happened to need — clearly wrong for a row that's obviously "the rest of a normal table, minus one column."

Given that, the formatter deliberately does NOT pad a sparse row's missing cells with `| |`:

- **Padding would erase the round-trip signal.** A padded sparse row (`| text | | | | |`) is byte-for-byte what a wrapped continuation row of a FULL row looks like once its wrapped column's text is gone from later lines. If sparse rows were padded, there'd be no way to tell "this was authored short" from "this is a continuation row I wrapped myself" on the next parse — exactly the ambiguity that caused the first bug below.
- **It shouldn't drive column width on its own.** A sparse row's one real cell isn't tabular data sharing column 0 with every other row — it's a whole-row note. `computeColumnWidths` and `computeGroupWidths` both exclude sparse rows from their input, so a long comment can't unilaterally force every other row's real columns wider (or, under cross-table matching, widen a sibling table's columns too).
- **Pipes still stay aligned — the real columns grow to meet it, up to `tableWidth`.** `widenForSparseRows` compares the widest sparse row's own rendered width against the real columns' natural total and, if the sparse row is wider, grows every real column evenly (remainder to the first few) to close the gap — the same "alignment always wins" guarantee width-0 already makes for a monster cell in a real column, extended to a monster row instead of a monster cell. At `tableWidth: 0` this is unconditional (alignment always wins, full stop); at a nonzero width the growth is capped at `tableWidth` — real columns use whatever headroom the target leaves after their own content, but never grow past the target just for the sparse row's sake (see the second bug below). A sparse row narrower than the table just gets its own trailing cell padded out to match, real columns untouched.
- **Whatever doesn't fit even at `tableWidth` wraps — at the table's FULL width, not one column's slice of it.** A sparse row isn't really "in" any one column, so when it still needs to wrap after the widening above, `emitTable` gives it the whole row's available width rather than confining it to column 0. Every physical line keeps the row's original (sparse) cell count — that's the signal `collapseContinuationRows` uses to fold them back into one logical row on the next parse: two adjacent rows with the SAME cell count, both less than the header's, are always parts of one wrapped sparse row (see the third bug below for why this used to be unsafe, and the function's own comment for the one accepted edge case — two genuinely independent adjacent sparse rows of matching arity merge too).

**The first bug this fixed:** an earlier version padded every row — sparse or not — out to the header's column count before doing anything else, in `scanTables`. At `tableWidth: 0` this happened to look fine (a sparse row rendered as `| text | | | | |`, visually a comment). But at any wrapped width, if that sparse row's cell was long enough to need wrapping, `emitTable` produced continuation lines with text in cell 0 and blanks elsewhere — and `collapseContinuationRows` only recognized a continuation by an EMPTY first cell, so it never merged them back. Each wrapped line became its own permanent phantom row on the next format pass: one sentence, silently and permanently split into three separate one-cell table rows. Fixed by keeping a sparse row's true (smaller) cell count all the way through `scanTables`/`emitTable`/`minifyTable` instead of rounding it up to the header's column count anywhere in the pipeline.

**The second bug this fixed:** `widenForSparseRows` originally ran unconditionally and uncapped, at every `tableWidth`. A sparse row's own content had no upper bound at the time — nothing wrapped it — so at a nonzero target width, a sufficiently long comment forced EVERY real column to widen to match it, blowing straight through the requested width for the whole table (a 5-column table asked to fit 70 characters came out at 123, because one comment cell needed 123). That's a categorically bigger deviation than the shrink loop's existing "wider than asked" allowance for a single unbreakable token, which overflows by at most one word. Fixed by capping the widening at `tableWidth` (see the fourth bug below for why an outright cutoff at width 0 vs. width N wasn't the right fix either).

**The third bug this fixed (superseding the "can't be safely wrapped" reasoning above):** the fix for the second bug initially disabled widening entirely at any nonzero width, leaving a sparse row unwrapped — correct for not blowing through the target, but it meant a long sparse row still overflowed the target ON ITS OWN, just without dragging the rest of the table along. The actual ask was for it to wrap (fold) like everything else once widening alone couldn't fit it. Wrapping was avoided at first because a full row's continuation rows are recognized by an EMPTY first cell (the wrapped text is assumed to live in a LATER column) — but a sparse row's text starts in cell 0, so its wrapped pieces have the same empty-elsewhere shape as a genuinely new short row, with no way to tell them apart under that rule. The fix widens what counts as a continuation instead of trying to reuse the empty-first-cell rule: `collapseContinuationRows` now also merges any sparse row whose cell count matches the row directly above it, since `emitTable` gives every physical piece of a wrapped sparse row that same (original) cell count. A full row's continuation still can't land on a sparse row or vice versa — arity has to match on both sides — so the two mechanisms can't cross-contaminate each other.

**The fourth bug this fixed:** even after wrapping worked, `widenForSparseRows` was still gated on `tableWidth === 0` — an outright on/off switch rather than a cap. So at any nonzero width, a sparse row wrapped against the real columns' own natural (unwidened) total, even when `tableWidth` had plenty of headroom above that natural total to fit the whole sparse row on one line. A table asked to fit 160 characters, whose real columns naturally settled at 66, kept wrapping a 123-character comment in two — because its wrap budget was 66, not the 123 (or up to 160) actually available. Fixed by making `widenForSparseRows` take `tableWidth` (or `Infinity` at width 0) as an explicit cap rather than a gate: real columns now widen to use exactly as much of the target as the sparse row needs, up to the target itself, and only wrap whatever still doesn't fit past that.

**A fifth, long-open issue — now resolved, but not retroactively:** `collapseContinuationRows` requires a continuation row's *first* cell to be the empty one — the wrapped text was assumed to live in some *later* column. A FULL row (as many cells as the header) whose column 0 is the one that needs to wrap broke the same way sparse rows used to: its continuation lines had text in cell 0 and blanks elsewhere, indistinguishable from a short row, and never got merged back — a real, reproducible bug in ordinary tables (no sparse row involved at all) whenever the longest content happened to live in the leading column. This is exactly what grid tables (below) were built to eliminate structurally: a grid table's continuation lines are bounded by the same border on every side, in every column, so there's no "which cell is empty" heuristic to fool in the first place. **Important:** this only fixes it going forward — a file that already has this bug's symptom baked in (e.g. `Inhaled Oxygen` / `Concentration` sitting as two separate table rows from an earlier bad save) stays exactly as fragmented as it is; nothing in this formatter can recover information that's already been split across two logical rows on disk. Only a fresh wrap, from an unfragmented source, gets the fix.

### Grid tables (width N)

At any nonzero `tableWidth`, a table is written as a **grid table** — the Pandoc/reStructuredText style, `+---+---+` borders and `|` content lines — instead of plain GFM pipe syntax. `grid-tables.ts` owns this engine end to end: parsing (`scanGridTables`), the width-0 conversion (`gridToParsedTable`/`parsedTableToGridTable`), and emission (`emitGridTable`). `markdown-format.ts`'s `formatMarkdown` finds every table block regardless of which syntax it's written in (`scanAllTables`, combining `tables.ts`'s `scanTables` and `grid-tables.ts`'s `scanGridTables` into one document-order list) and dispatches to the right engine purely on `tableWidth`: **0 always emits plain pipe syntax, N always emits a grid table — regardless of which syntax the SOURCE used.** A hand-authored grid table gets flattened to pipe syntax the moment someone asks for width 0; a plain pipe table gets grid syntax the moment someone asks for width N.

**Why cell boundaries are read by DELIMITER, not by character position.** An early version fixed a column-position set once from the table's top border and required every content line, everywhere in the table, to have `|` at exactly those character offsets — a structural read, immune to the "empty first cell" ambiguity that made the old pipe-table wrap convention unsafe. But it had a fatal usability gap: the entire point of a grid table is that a person can hand-edit a cell's text — widen "Inhaled Oxygen" to "Inhaled Oxygen Concentration" — and expect `codon-format` to reflow the WHOLE table back to a clean, consistent width on the next pass. A real edit like that shifts every `|` after it in that row without touching any other row's positions, and a position-anchored parser reads that as "this line no longer matches the table," ending the block scan right there — not just misreading the edited row, but treating every row below it as unparsed leftover text too, exactly the bug report that prompted this rewrite. Fixed by reading each content line's cells via `splitTableRow` (the same literal-`|`-delimiter split the plain pipe-table engine already uses) instead of matching character positions — a row can drift arbitrarily far from its neighbours' widths and still parse correctly; `emitGridTable` re-establishes consistent alignment for the whole table on the very next pass.

**Recovering a genuine PARTIAL colspan (not the classic whole-row note) under a delimiter-only read.** A band with exactly `cols` cells is unambiguous (one cell per column, in order); a band with exactly 1 cell is the whole-row note. A band with some OTHER cell count — say 2 cells in a 3-column table — is genuinely ambiguous by count alone: which of the 3 columns did the 2 cells cover? `snapBandToColumns` resolves this by finding this band's own `|` character positions and matching each to the NEAREST of the header row's own `|` positions — tolerant of drift (the band doesn't need to align with anything precisely), but it requires the header itself to currently be a clean, full-width reference and the resulting mapping to be unambiguous (strictly increasing, spanning column 0 through `cols`). When that snap can't be resolved — an edited or otherwise-inconsistent band — the shortfall is treated as trailing and padded with blank cells at the end, the same graceful degradation `tables.ts` already applies to a merely-ragged plain pipe-table row. This is a deliberate trade: a partial colspan surviving a hand-edit to ITS OWN row, or to an unrelated row, keeps working; a partial colspan combined with an edit that ALSO breaks the header's own alignment degrades to "trailing blank" rather than corrupting anything.

**Border-merge drawing rule:** at an internal column boundary, the emitted border shows a real `+` only if BOTH the row-band above and the row-band below have a genuine divider there; if EITHER band spans across that boundary, the border omits it (a continuous dash run) so the drawing doesn't contradict the content. This is purely cosmetic — parsing never depends on it — but it's what makes a spanning cell actually look merged instead of sitting inside a fully-gridded box its own content line ignores.

**Width-0 flattening (`gridToParsedTable`) is a one-way simplification, by necessity.** Plain GFM pipe syntax cannot represent a partial colspan or a row span at all — there is no structural equivalent. So at width 0: a cell spanning every column becomes the pre-existing single-cell whole-row note (unchanged, see "Sparse rows" above); a PARTIAL colspan places its text at the anchor column and leaves the columns it covered blank (never duplicated — a merged value belongs to the group, not to each column); this is documented as a deliberate, narrow exception to this package's otherwise-lossless-at-a-given-width guarantees — content itself is never dropped, only the fact that specific cells were merged, which nothing in plain pipe syntax could carry anyway.

**Cross-table width matching (`alignTablesWidth`) is scoped to spanless tables.** A table containing a PARTIAL colspan is excluded from grouping entirely (sizes standalone) — generalizing "same column lines up across tables" to tables with different span shapes isn't well-defined without also deciding how spans align against non-spanning siblings, and nothing has needed it yet. A table using only the pre-existing whole-row-note convention (`colSpan === cols`) still groups exactly as it always has — that convention predates grid tables and was never blocked from grouping (`computeGroupWidths` already excluded sparse rows row-by-row, not table-by-table).

**`reflow.ts` needs to know about grid tables too.** Before this, `reflow.ts`'s only "is this a table line" check was `trimmed.startsWith('|')` — a grid table's `+---+---+` border lines don't start with `|`, don't match the thematic-break/setext regex either (mixed `+`/`-` characters), and would otherwise fall through into ordinary paragraph-joining and get glued into prose. `reflow.ts` now also checks `computeGridTableBlockLines` (mirroring how it already skips MDC blocks) before any of that logic runs.

**Phase 1 scope — row spans are not yet supported.** A cell spanning multiple ROW-bands vertically needs a genuinely harder algorithm (distributing extra height across the bands it covers, generalizing the shrink-to-fit floor logic across a rowspan's bands) than colspan alone. `scanGridTables` recognizes the row-span border marker (a blank, space-filled segment) and, on seeing one, abandons parsing that block entirely rather than guessing — the block is left completely untouched, exactly as if it weren't a grid table at all. This is deliberate and documented, not an oversight; row-span support is planned as its own, separately-scoped follow-up.

### Cross-table width matching

Opt-in via `formatMarkdown`'s `alignTablesWidth` option (default `false`; the CLI exposes the same switch as `--align-tables-width`, see below). When set, tables with an **exact header match** — same cell text, same column count, same order, anywhere in the same document — share one set of column widths, computed as if all their rows (one shared header + every table's body rows, concatenated) were a single table. Implementation: `scanTables`/`emitTableLines` split table-block *discovery* from *emission* specifically so `formatMarkdown` can group same-header tables and pre-compute shared widths before any of them render when the option is on — a table's own width is otherwise always computed standalone (`computeColumnWidths` on just its own rows). The option only gates the grouping step in `formatMarkdown` itself — `scanTables`/`emitTableLines`/`tableHeaderKey` are unconditional; a caller computing widths directly from `tables.ts` always gets standalone widths unless it does the grouping itself.

This exists because a document with several tables sharing a schema (one per section — a repo inventory, a per-environment config table, whatever) reads far better with visually consistent columns than with each table independently squeezed to its own narrowest content. Matching is **exact text**, not fuzzy/order-insensitive — two tables with the same labels in a different order are treated as different schemas on purpose; silently re-mapping columns by label would be a much riskier, harder-to-predict transform for comparatively little benefit.

## The CLI (`codon-format`)

### `--check` is a general gate, not a commit-only one

`--check --width N` validates against whatever width you asked for — it does **not** silently coerce to 0. Early on this package briefly *rejected* `--check` combined with a nonzero `--width`, on the theory that `--check`'s only legitimate use was "is this safe to commit" (which is always width 0). That was reverted: it's the caller's call whether they want to gate on some other width (testing, debugging, a downstream project with its own on-disk convention) — the CLI trusts the caller rather than enforcing one opinion about what `--check` is for. What's true regardless: **only width 0 is safe to commit** (see above) — that's documentation/guidance, not something the tool polices.

### Auto-fix vs. gate — pick the one that matches where you're calling it from

- **CI** (a PR check that shouldn't silently mutate the branch): `codon-format $(git ls-files '*.md') --check`.
- **Local pre-commit hook** (friendlier — let it fix and continue, the way `prettier --write` does under lint-staged):
  ```bash
  files=$(git diff --cached --name-only --diff-filter=ACM -- '*.md')
  [ -z "$files" ] && exit 0
  npx codon-format $files
  git add $files
  ```
  `--check` in a *local* hook just means "fail the commit and make the human re-run the formatter themselves" — usually not what you want for pure formatting.

### Project-wide discovery: `--git-driven`/`--all`

Two mutually exclusive flags trigger discovery instead of formatting the positional file arguments: `--git-driven` (delegates to `git ls-files`, so it respects `.gitignore`; falls back to `--all`'s behavior, with a stderr notice, when `--root` isn't a git working tree or `git` isn't installed) and `--all` (an explicit opt-in plain filesystem walk that never touches git and ignores `.gitignore` entirely). `--root <dir>` sets the discovery root (default cwd); `--ignore <pattern>` (repeatable) adds exclusions on top of the two defaults (`.git`, `node_modules`), which are always merged in and can never be removed. With no file arguments and neither discovery flag, the CLI defaults to `--git-driven` from cwd rather than erroring. The same discovery is exposed programmatically as `discoverMarkdownFiles` (paths only, no bundled formatting) for a consumer like `jurijsk/codon` that imports the formatter directly rather than shelling out to the CLI.

Implementation lives in `discover.ts`; the full design writeup is in [docs/project-wide-discovery-spec.md](./project-wide-discovery-spec.md).

## Known pitfall: watch for control bytes silently introduced by editing tools

`tableHeaderKey`'s join separator was briefly a **raw NUL byte (U+0000)** instead of the literal text `.join(' ')` — an editing-tool artifact, not a deliberate choice. It didn't break anything at *runtime* — JS strings permit embedded NUL bytes — but it made the file register as **binary** to git, grep, and most text tooling (`git diff` alone would not have caught it — this was found via a stray `grep` returning "binary file matches"). Fixed in `v0.1.1`. If a file that is plainly text ever gets treated as binary by tooling, check for stray control bytes before assuming it is a tooling bug.

## Known pitfall: a duplicated fence-toggle silently hid content twice (`v0.2.2`/`v0.2.3`)

`mdc.ts`, `tables.ts`, and `list-tighten.ts` each used to keep their own local `inCode`/`inComment` booleans to skip over fenced code and multi-line HTML comments, hand-typed rather than shared. A commented-out fenced code cell (`<!-- \`\`\`{r} … \`\`\` -->` — a real Quarto pattern for a dormant code chunk) embeds a fence marker mid-line inside the comment; a naive scanner that only checks "does this trimmed line start with `` ``` ``" sees that embedded marker as a real fence open/close and flips its toggle. Once flipped, the scanner believes it's inside a code block for the rest of the file — silently hiding every MDC block (`v0.2.2`) or every table (`v0.2.3`) after that point. The two bugs were the *same* mistake, found and fixed independently in two different files, because the scanning logic itself was duplicated rather than shared. `reflow.ts` never had this bug — it solves the problem a structurally different way (it consumes a whole comment's lines directly, never letting the fence check see them) — but `frontmatter.ts` has never needed fence-awareness at all, so it isn't part of this pitfall.

Fixed in `v0.2.3` by extracting `fences.ts`: one shared `computeFenceProtectedLines` (plus the `isFenceMarker` / `isCommentOpener` / `isCommentCloser` predicates it's built from) that `mdc.ts` and `tables.ts` now both call instead of reimplementing the scan, and that `list-tighten.ts` and `reflow.ts` use for the marker checks their own, differently-shaped control flow still needs. If a third copy of "is this line inside a fence/comment" ever gets hand-written again instead of importing from `fences.ts`, that's the bug recurring a third time.
